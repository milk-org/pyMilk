```
pip install -e .
```

(`-e` recommended). If getting into dependency hell, the following makes the cmake process much easier to debug, and also for a faster recompile if only C files have been modified:

```bash

```

## Endpoint library

The C++ emit/recv endpoints have a fairly simple API -- see `Transport-engine/include_cpp/transport_{recv,emit}.hpp` -- below is a replay with some notes.

### Recv

```cpp
RecvTransport(const char *name) {strcpy(name_, name);};
```
Initialize from a `name`. A `name` is a `<proto>::<address>` string. Future: in the abscense of `<proto>::`, should default to SHM.


```cpp
// Public interface - read-only
IMAGE_METADATA       *md() const { return md_; } // The metadata describing the data, even if there is no underlying IMAGE. Size, shape, counters...
void                *ptr() const { return ptr_; } // The naked pointer to the data buffer. Is on device <req_>.
InternalStorageEnum  req() const { return req_; } // A device location -- -1 for CPU RAM, >= for GPU RAM. Could extend to distinguish NUMA locations.
```


```cpp
// Pure virtual
virtual void     init_storage_target(InternalStorageEnum req) = 0;
```
Post-init -- request the data buffer to be allocated on device `req_`. Why post init ?
```txt
Caller of the recv transport just knows the name of the endpoint
                                     calls constructor ----
                                                       ---- endpoint object is "partially" created by ctor,
                                                            but knows which protocol is going to be used
Caller can poll whether transport is GPUdirect capable ----
                        or has preferred NUMA affinity
                 Caller requests preferred req_ device ----
                                                       ---- endpoint marks requests for req_ device
                                            first data message comes in
                                                       ---- endpoint performs deferred init, now that the size is
                                                            known from message header, and allocates buffer
                                                            on req_ device
```


```cpp
virtual void     print_type() = 0;   // Just a string
virtual SyncEnum sync_barrier() = 0; // Block until new data or timeout, return is SUCCESS, TIMEOUT, FAILED, FATAL
virtual void     move_new_data_to_requested() = 0; // Maybe I have to obsolete that. sync_barrier promises the temporality of new data
                                                   // is respected, but not that new data is under ptr_ yet.
                                                   // This function promises that, in case a double copy is needed.
```

### Emit

```cpp
EmitTransport(const char *name, IMAGE_METADATA* md_request) {strcpy(name_, name);};

// Public interface - read-only
IMAGE_METADATA       *md() const { return md_; } // Describes data
void                *ptr() const { return ptr_; } // Put data here before sending
InternalStorageEnum  req() const { return req_; } // Device, as for the receiver

// Pure virtual
virtual void init_storage_target(InternalStorageEnum req) = 0; // Same philosophy as for the receiver, ctor allows capability detection,
                                                               // and allocation is done by a second call.
virtual void print_type() = 0; // Just a string
virtual void move_and_publish_data(struct timespec* atime) = 0; // Takes what is under ptr_ and sends it.

bool _initialized = false; // Future use ?
```

## Supported protocols

- ImageStreamIO SHM: use `shm::<name>` on emit and recv.
- ZMQ PUB/SUB, over all the supported ZMQ transports, eg:
  - IPC: recv & emit: `zmq::ipc:///tmp/zmq_ipc_location`
  - TCP: emit: `zmq::tcp://127.0.0.1:12345` -- recv: `zmq::tcp://12345` -- _some version of ZMQ don't DMS resolve, even 'localhost' won't work over 127.0.0.1_
- MILK TCP -- optimized P2P handshake and packet send. Emit: `tcp::127.0.0.1:12345` -- recv `tcp::12345`

- Coming soon: MILK's UDP multicast/unicast...
- And then we can think about MUDPI et al.

## Python bindings

Bindings implemented in `milkengine/transport_python_module` using nanobind.

There's simple bindings to the API above, and copy-on-read (`copy`) and zero-copy (`view`) access to the data buffers (and `write` for Emit endpoints), transformed into numpy or cupy arrays appropriately.

There's a very shallow pure-python binding at `pyMilk.interfacing.transport` that simply ensures a few loading hack of the compiled extensions.

## Tests and demo

Using pytest.

Relevant tests are located at `tests/interfacing/transport_test.py` and can be run with e.g.
```bash
pytest -xv ./tests/interfacing/transport_test.py
```

The various protocols are tested for:
- Connection / deconnection
- Data integrity
- Seamless reconnect if the receiver or emitter drops and respawn.

The main test process write data to a SHM `mproc_emit_relay` and retrieves the same data from `mproc_recv_relay`:

```
Main                   Emit process                       Recv process

1
post mproc_emit_relay --> 2 get from mproc_emit_relay
                          3 send into emit endpoint     --> 4 receives into recv endpoint


6                       <---------------------------------- 5 posts mproc_recv_relay
receives same data in
mproc_recv_relay.


Run with
```bash
pytest -v ./tests/interfacing/transport_test.py
```
